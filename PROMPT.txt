城市里一个孤立十字路口该几秒一个信号周期，看着简单，其实是流量比、损失时间和延误三者拧在一起解出来的。周期短了车排不完、周期长了空放绿灯照样堵，交通工程师需要一个能把 Webster 那套配时公式算准、还能扫一遍候选周期看延误怎么变的后端，替他们在渠化方案之间做比选。这个服务只解孤立交叉口的解析配时，经 HTTP 供上游的配时工具调用，不做路网仿真、不带界面。

一次配时提交的是各相位的到达流率 q（辆/时）、饱和流率 s（辆/时）和每周期总损失时间 L（秒）。核算沿这条链展开：各相位流量比 y = q/s，总流量比 Y = Σy；未指定周期时按 Webster 最佳周期式 C0 = (1.5L + 5)/(1 − Y) 求周期；有效绿按流量比分配 g = (C − L)·y/Y，且所有相位有效绿之和加上损失时间必须严格等于所用周期，这个等式的残差要压进容差、不允许绿灯时间凑不平还照样往下算。均匀延误取 Webster 第一项 d = 0.5·C·(1 − λ)²/(1 − λ·x)，其中绿信比 λ = g/C、饱和度 x = q/(λ·s)，再由此给出每相位的总延误率 q·d 与整个交叉口的合计延误。校验要卡在公式之前：相位数少于两个、某个 q 为负或 s 不为正、损失时间不为正的，一律回带原因的错误结构。

饱和是这类核算最容易翻车的边界，要分两层防住。整体层面，当 Y 达到或极其接近 1（钉一个裕度，比如离 1 不足 0.01）时，最佳周期会趋于无穷，服务必须在求解前就判定过饱和、返回专门的错误并附上算出的 Y，绝不能吐出一个负周期或几千秒的假周期糊弄过去。相位层面，即便 Y 小于 1，某个相位也可能因为绿灯被别人挤占导致饱和度达到或超过 1，这时该相位要单独报出饱和错误，而不是默默算出一个没有物理意义的延误。若调用方设置了各相位最小绿，先保住最小绿再把剩余时间按流量比分配；保不住就报错，不许把某相位绿灯悄悄削成零还照旧输出它的延误。

服务对外提供三件事：交入相位与损失时间，返回 Y、最佳周期与各相位绿信比；再交入（或另指定一个周期）返回各相位均匀延误、饱和度与合计延误；第三件是把一组候选周期扫一遍，回一条「合计延误随周期变化」的曲线点列，让工程师看到延误先随周期缩短而降、过了某点又因绿灯空放回升的整条走势。曲线上每个点都要用该周期对应的那套绿信比现算延误得来，不许预先存一条曲线直接回放；扫描是可中断的长作业，中途被取消时绝不能把只算了一半的点列当成完整结果交出去。配时工况可按名字建档、日后凭名字取回重算，服务预置一组四相位算例（Y 约在 0.7、损失约十几秒、最佳周期落在文献常见的五十到八十秒区间），任何人拉起服务都能拿它对数。多份工况并行核算时，各自的流量比、周期与延误互不串扰。

自动化测试要逐条锁住这些关系：只增大总损失时间、其余不动，最佳周期上升、各相位均匀延误不下降；只把某相位到达流率加倍（仍保持 Y 小于 1），该相位流量比与绿信比上升、其余相位绿灯被挤占；Y 趋近 1 时周期急剧变大，一旦越界两条配时路径都不给出正的有限周期；用「指定周期恰等于自动算出的 C0」去核算，绿信比与延误必须与自动周期在容差内一致；所有有效绿之和加损失时间等于所用周期。测试要专门盯住流量比与延误必须共用同一组到达率——配时用一套 q、延误却用另一套 q，是这里最隐蔽的错。

用 Node.js 20 搭配 TypeScript，Web 层用 Fastify，把流量比与周期求解、绿信比分配、均匀延误、饱和判定、周期扫描、工况档持久化与 HTTP 路由拆成彼此独立的模块，别让配时闭式和延误扫描堆在一个文件里。工况档存到 PostgreSQL 16。交付 Docker 编排，服务连同数据库一次构建就能拉起对外提供接口，随附的自动化测试跟着构建跑，覆盖四相位算例的数量级、过饱和拒绝、损失增大周期增大、扫描点列现算与并发隔离。
